Settle this first

Will the Platform Run Your Code Inside the Member's Own Tenant?

It is a property of the platform, not a choice you get to make.

The answer decides who operates the integration, where credentials live, whether connector faults are isolated to one member or shared across all of them, and whether shipping a fix means asking every member to upgrade. Ask it before scoping anything, because it is what makes route one or route two the natural fit — and the platforms that answer "sort of" are where the design work is.

Yes — in-tenant Salesforce and Dynamics say yes and get managed packages the member installs. You build against the API or the SDK, and the member operates it.
No — gateway Intercom says no, so TSANet hosts and operates the adapter on the Connect Gateway. You write only the half that talks to your platform.

The taxonomy, the consequences of each class, and what to do when a platform answers both ways: Two Ways to Build a Connector. The worked case of an ambiguous answer is the ServiceNow assessment.

Build on the Connect Gateway

TSANet supplies the engine, the contract and a conformance harness that certifies the seam; you write only the half that talks to your own platform — and never touch the Connect API or its errors. The least effort, and the route for any platform that will not run your code in the member's tenant. The repository is private; adapter authors get access at onboarding.

Design & adapter guide → v2.0.0 · Java

Use the SDK

A Java client over the Connect API with typed facades, validation and both auth modes, published as a public package. The shortest path on the JVM that is not hand-rolled HTTP, and the one that already encodes the API's sharp edges.

Build Against the API

The translation-service pattern: your platform's events in, Connect API calls out, updatedAfter polling back. For any stack that is not the JVM. Read the behaviour guide before you design; the reference alone will not tell you about the default error mode or the webhook version trap.

Sequence

The First Week, Whichever Route

  1. Get a Beta account from membership@tsanet.org, and if you will use OAuth client credentials, have TSANet provision your service principal at the same time — an app-only token is not accepted until they have.
  2. Call GET /v1/me and confirm the company your credentials resolve to. Every call is scoped to that identity.
  3. Fetch a partner's process form fresh and submit a case with testSubmission: true. Nothing you send reaches a real partner while the flag is set, and the documentId you must submit comes from that fetch.
  4. Read it back. The shape you write is not the shape you read, and responded, not the status name, is what gates the SLA. TSANET-2026-001 is the map.
  5. Send the Accept header on every call — Accept: application/json, application/problem+json — or every rejection arrives as HTTP 500 and looks like an outage.
  6. Persist the token at creation, before anything else in your flow can fail. There is no idempotency key on create; a blind retry is a second case.
  7. Subscribe to webhooks on v2, verify the signature before processing, fast-ack, and keep a poll behind the push — delivery is at-least-once and the fetch is what establishes truth.

Each of those is a section of Working with the API, which exists because the reference does not say them.
