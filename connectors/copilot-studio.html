Microsoft Copilot Studio, with Claude

Not a connector, and not built. A platform assessment for members who want an agent in Copilot Studio — running on Claude Sonnet — to read and act on TSANet Connect cases. What Microsoft actually ships, which admin switches gate it, the three routes from an agent to the Connect API, and the questions nobody has answered by trying it yet.

Read this before you use anything below

Every claim on this page is documented, not observed. It was read on Microsoft Learn or in the source of the shipped Dynamics solution; nobody has yet built a Copilot Studio agent against TSANet Connect and watched it work. The one exception is the Dynamics solution itself, which is a shipping connector — the untested part is putting an agent in front of it.

Treat this as a research map with citations. Anything marked needs probe is a known unknown rather than an oversight, and the list of them at the bottom is short enough that a member with a Power Platform environment and an afternoon could close most of it.

The model

Which Claude Copilot Studio offers, and where it runs

Copilot Studio lets a maker pick the agent's primary model from a dropdown on the agent's Overview page, and pick a model again, separately, for each prompt tool. Anthropic models appear in both places once an admin has switched them on. Since 7 January 2026 Anthropic operates as a Microsoft subprocessor for these models, so the Microsoft Product Terms and Data Protection Addendum apply rather than Anthropic's own commercial terms — except for models Microsoft labels "with Data Retention", which stay off by default everywhere and need a separate opt-in. documented

Claude models a maker can pick, from the availability tables on Microsoft Learn. "Cross-geo" means the request may be processed outside the tenant's region; only United States tenants avoid it.

  • Two Learn pages disagree about Claude's status in prompt tools. The March 2026 release notes say Claude Sonnet and Opus are "generally available globally (excluding GCC)". The prompt-builder settings page, updated in August 2026, says "Anthropic Claude models are at the experimental stage, even though they don't display a tag" — and experimental models are subject to preview terms and not recommended for production. The two pages have not been reconciled; a member deciding whether an agent is production-grade should ask Microsoft which is current rather than pick one. documented
  • The same two pages disagree about hosting. The subprocessor page says Microsoft's terms and DPA govern Anthropic models; the prompt-builder page still says "Anthropic models are hosted outside Microsoft and are subject to Anthropic terms and data handling". The subprocessor page is dated later (10 September 2026) and is the admin-facing one; the hub reports both. documented
  • Content moderation is Microsoft's slider, and it is unavailable for Claude. The per-prompt content moderation level applies only to Microsoft-managed models; the control is disabled when an Anthropic or Foundry model is selected. Temperature still applies. documented
  • If an admin revokes Anthropic after agents are built, they do not stop cleanly. Agents switch to "another suitable internal model" if one exists, and error out if it does not, until a maker changes the model by hand. Design the agent's instructions to hold up on GPT-4.1 as well, because that is the fallback. documented
Why not Haiku. Claude Haiku 4.5 is generally available in Microsoft Foundry, in both the Azure-hosted and Anthropic-hosted variants, but Copilot Studio does not list it anywhere. The only documented way to bring a Foundry model into Copilot Studio is Bring your own model for prompts, which requires a chat-completions endpoint (a URL ending in /chat/completions) and lists no Anthropic models; Claude in Foundry is served through the Messages API at /anthropic/v1/messages instead. documented Whether any shim makes a Foundry Claude deployment answer on a chat-completions URL is untested needs probe — and even if one did, that route reaches prompt tools only, never the agent's orchestration. Sonnet 4.6 is the practical floor.

Prerequisites

Three switches, in two admin centres, before a maker sees Claude

A maker who cannot see Anthropic models in the picker is almost always missing one of these. They are tenant-wide, environment-scoped and region-dependent respectively, and they are owned by different roles.

  • Access is per user, not just per tenant. The subprocessor setting takes a user or security-group assignment, and it is enforced across Copilot Studio: a user outside the assignment cannot use an agent that runs on Claude. Plan the group before the pilot, not after the first "it works for me" report. documented
  • Preview models and external models are separate gates. An admin can allow Claude and block previews, or the reverse. Sonnet 4.6 is GA and external, so it needs only the external-model gate. documented
  • Compliance exclusions are explicit. Anthropic models in Copilot Studio are outside the EU Data Boundary; FedRAMP is not achieved; PCI DSS does not apply; and the Copilot Studio government-cloud table lists no Claude model at all. A member in any of those positions should stop at this row. documented

Architecture

Three routes from an agent to the Connect API

Copilot Studio gives an agent tools; what a TSANet agent needs is a tool that reaches Connect. There are three shapes, and the platform's own rules — not preference — decide which one a member can use.

A

Sit the agent on the Dynamics connector

The Dynamics solution already installs six Dataverse tables — the case, its notes, the mapping and settings tables — and a set of Power Automate flows that do the Connect calls: a Login child flow that holds the client-credentials exchange in one place, and flows for fetching cases, posting a case, posting a note, and posting or updating an approval. All of that is in the public repository. documented

A Copilot Studio agent in the same environment can use Dataverse as a knowledge source and can call flows as tools, so the shape is: read ap_ tables directly, and write by invoking the solution's own flows rather than the API. The agent never sees a Connect credential, the connector's log table records what happened, and the whole thing stays in the member's tenant — the in-tenant class, with no new operator. Nothing on this route has been wired up and tested. needs probe

This is the route to try first, and the reason this page lives next to the Dynamics one: for a Dynamics member it adds an agent to something that already works.

B

Give the agent the API directly

Copilot Studio's REST API tool (preview, standard harness only) takes an OpenAPI specification — v2, as JSON; a v3 file is translated on upload — plus one of three auth shapes: none, an API key, or OAuth 2.0 with client id, secret, authorization URL, token URL and a consent card shown to the user in chat. That last shape is an authorization-code flow: it exists to let an individual user sign in. documented

The Connect API's server-to-server path is OAuth 2.0 client credentials: app-only, no user, against a service principal TSANet provisions and maps to the member company. There is no user to redirect, so the wizard's OAuth option does not fit; the hub's reading is that a Copilot Studio REST tool cannot authenticate to Connect as documented. Community write-ups say a Power Apps custom connector accepts a Client Credentials grant, and one forum thread reports Copilot Studio still sending a delegated token at runtime for such a connector. community Both need a probe. needs probe The fallback that certainly works is the one route A already uses: a Power Automate flow with an HTTP action doing the exchange itself.

Two smaller things. The public API reference is the GitBook reference and a Postman collection; the OpenAPI file the SDK is generated from is obtained through TSANet, so ask membership@tsanet.org for it before designing around a spec upload. And by default most Connect rejections come back as HTTP 500 unless the caller sends the Accept header that switches on RFC 7807 bodies — whether a REST tool can send that header is unverified, and without it the model will read every validation failure as an outage. needs probe

C

Put an MCP server in between

Both harnesses can attach a Model Context Protocol server as a tool: the standard harness through an onboarding wizard (or a custom connector whose OpenAPI stub carries x-ms-agentic-protocol: mcp-streamable-1.0), the GitHub Copilot harness through its Build tab, in preview since July 2026. Only the Streamable HTTP transport is supported — SSE was dropped in August 2025 — and auth is none, API key, or OAuth 2.0 in three flavours including dynamic client registration. Because access rides on Power Platform connectors, the tenant's data-loss-prevention policies govern it too. documented

What does not exist is the server. TSANet publishes no MCP server for Connect, and none of the shipped connectors expose one. Building one is the same translation-service work described in Working with the API, hosted somewhere reachable from Copilot Studio, with the client-credentials exchange inside it — which makes it a small gateway-class component, operated by whoever hosts it. Microsoft's MCP certification programme (preview) exists if it were ever to be listed. Until someone writes it, this route is a design, not an option.

Runtime

The harness decides the model and the tools together

Copilot Studio runs agents on one of two harnesses, and since June 2026 the choice is real. It matters here because the Claude model and the Connect tooling are not chosen independently: each harness admits a different Claude and a different set of tool types. documented

  • Sonnet 5 costs you the REST API tool. The REST tool and the prompt-builder model settings are documented for the standard harness only. An agent that wants Sonnet 5 is on the newer harness, where the documented ways to reach an external API are an MCP server or a workflow — which pushes it toward route C, or route A through a workflow. documented
  • A conversational turn is many model calls. The standard harness does not enforce a token limit across the planner, retrieval and tool-summary calls that one user message triggers; the 200K context window applies per call. Long case histories pasted into a prompt tool are the place this bites. documented
  • Every new agent gets a Microsoft Entra Agent ID from July 2026, and the environment-level opt-out is gone. That identity is what conditional-access and connector permissions will be scoped to; it is not a Connect identity, and it does not replace the service principal TSANet provisions. documented

Design

What the model does not change

Everything on the API page still applies when the caller is a language model, and a few of those rules become sharper rather than softer.

  • Accepting is a commitment, so the agent must not do it alone. Approval stops the SLA clock and tells a partner an engineer is engaged. The shipped connectors disagree about automated acceptance, and the acceptance topic works through when a rule asserts something true. An agent that can call the approval endpoint on its own judgement is the "accept everything" posture with extra steps; give it the read tools and the note tool, and route acceptance to a person, as the Fin / Intercom connector does.
  • The token is the primary key, and the model will not remember it for you. Whichever route creates a case, the token has to be persisted by something that is not the conversation — a Dataverse row on route A, the server's own store on route C. There is no idempotency key on create, so a retried tool call is a duplicate case.
  • Forms are fetched fresh, because the required documentId arrives with the fetch and partners change their forms. Do not let the agent cache a partner's process form as knowledge.
  • Two note fields are two audiences. Internal notes and partner-visible notes are separate fields rendered as separate sections. An agent summarising a case for a partner must write to the right one, and a prompt that "adds a note" is underspecified until it says which.
  • Errors look like outages unless you ask otherwise. See route B: without the Accept header, a 400-class rejection arrives as HTTP 500, and a model reading that will retry, apologise, or both.
