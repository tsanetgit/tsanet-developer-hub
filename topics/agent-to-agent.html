Agent-to-Agent Support with TSANet

Support platforms now ship AI agents that can call outside tools and, increasingly, other companies' agents. Two open protocols carry that traffic. Neither says who an outside agent belongs to, what agreement covers the exchange, or which partner agent handles a given product, and those are the questions TSANet already answers for people. This page sets out what the protocols and the platforms support today, where a neutral member organization fits, the direction TSANet is considering, and what you can do with an agent and Connect right now. Nothing on the agent-to-agent side is built, and every claim says how it was checked.

The gap

What the Protocols Leave Open

The protocols make it technically cheap for one company's agent to reach another's. They solve the connection. They do not solve four things that two support organizations have to settle before their agents can work a mutual customer's problem:

QuestionWhat the protocols sayWhat TSANet does today, for people
Who is this agent, and which company answers for it?A2A lets an agent sign its own card. Verifying that the signer is who it claims to be is left to whoever runs a registry. No cross-company agent identity standard has been ratified.Vets members before they can open or receive a case.
What agreement covers what the two agents exchange?Out of scope for both protocols.One membership agreement in place of a contract between every pair of members.
Which partner agent handles this product, and what does it need to start?A2A describes curated registries but does not define one.The partner directory, and each partner's process form with its required fields.
What happened on the case, and who is accountable?Each side keeps its own task history.One case record that both members see, with a respond-by time.

The Two Protocols

What it does not coverShared memory or context between agents.Shared memory, and trust between organizations.
Extensions cannot change the protocol's core objects. An A2A extension may add structured data and metadata. It may not add fields to core objects or new task states. Any support-specific design therefore has to carry Connect's own case status beside the A2A task state, not in place of it. PRIMARY

Three things follow from the table.

  • MCP is the common ground today. A single MCP server could be registered in every platform listed. A2A reaches three of them.
  • The platforms disagree about sign-in. Some offer machine-to-machine credentials, some a fixed token, some only a signed-in user. One server has to satisfy all of them or leave some out. This is the same gap the Agentic usage topic found between hosted agent builders and code-first ones.
  • Platform agent identity stops at the company boundary. Microsoft's architecture guidance states that agent identities are single-tenant, and describes only one organization with several tenants. PRIMARY
Nothing here has been probed. No TSANet component has been registered in any of these platforms, and no primary source was found describing a cross-vendor support escalation running agent to agent in production. Treat the table as a reading list, not a compatibility matrix.

Direction

Three Pieces Under Consideration, None Built

The direction is to extend what TSANet already does for people to agents, on top of the open protocols, and not to invent a protocol or operate agents. Members' agents stay the members' own, on whatever platform and model they choose.

Proposed

An MCP Server for Connect

A hosted server a member registers once in its agent platform. Its tools find a partner, read the partner's process form, open a case, respond, add notes and close, under the member's own Connect credentials. It holds no cases; Connect stays the record.

Proposed

An A2A Support Extension

A published extension that says how a collaboration case travels as an A2A task: the fields a partner's form requires, how Connect's case status maps to task states, and how either side asks for a person to take over.

Proposed

A Member Agent Directory

A curated registry of members' support agents, in which TSANet attests that each agent belongs to a member in good standing. A2A leaves registries to implementers; the attestation is the part a membership body can supply.

Design rules the direction holds to

  • A person approves what a partner sees. Opening a case, responding and closing are partner-visible. The design assumes a human checkpoint on each by default.
  • A partner agent's output is untrusted input. Text from another company's agent can carry instructions aimed at the agent reading it. Case text is data and is never acted on as instruction.
  • TSANet carries the envelope, not the content. Where a member uses end-to-end encryption, the platform cannot read case text, so any content checks run on the member's side.
  • Works when only one side has an agent. A partner without an agent receives the case exactly as it does today.
  • Off until a member turns it on, and Beta first.

Mapping

A Collaboration Case as an A2A Task

Connect's case statuses line up with A2A's task states closely enough that a case can be carried as a task. The statuses below are from the Connect API specification. The mapping is a first pass, and which transitions Connect allows between them has not been checked on Beta.

Connect case statusA2A task stateNote
OPENSubmitted or workingWaiting for the receiving member to respond.
INFORMATIONInput requiredThe receiver has asked the submitter for more.
ACCEPTEDWorkingAn engineer is engaged on the receiving side.
REJECTEDRejectedFinal on both sides.
CLOSEDCompletedFinal on both sides. Connect has no reopen.

A2A's states are coarser than Connect's, so the Connect status would travel in the task's metadata and remain the authority. Notes map to task messages. NEEDS PROBE

Rules worth adopting now, whatever is built later

  • Keep a person on partner-visible actions. Accepting a case tells a partner that an engineer is engaged. The acceptance topic explains why a false acceptance is worse than a slow one.
  • Show the exact text before it is sent. Have the agent draft, show the partner-visible text to a person, and send only what was approved.
  • Make a retry safe. Model-driven clients repeat calls. Put your own case number on every case you open and look for it before opening another.
  • Treat everything a partner sends as data. Do not let case text or notes steer the agent.
  • Use test submissions on Beta until a person has watched the agent work a full case.
