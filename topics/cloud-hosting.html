Hosting an SDK Integration in Your Own Cloud

The Connect SDK is a library, so "hosting an SDK solution" means hosting whatever you wrapped around it: your own service, the console app, or the web demo. All of them share one runtime shape — a JDK 21 process that talks outbound HTTPS to the Connect API, keeps a SQLite cache on local disk, and reads its secrets from the environment — and that shape, not the cloud, decides what a correct deployment looks like. This page maps it onto AWS, Azure and Google Cloud, says what TSANet has actually run on each, and tags everything else as read from the vendor's documentation.

First question

Which of Four Things You Are Hosting

Nobody deploys connect-library. They deploy something that embeds it, and the four things that do have different needs from a host. Settle which one you are before you open a cloud console, because the answer decides whether you need a public URL at all, what you would lose if the filesystem vanished, and which secrets have to reach the process.

The shape

Six Things Every Cloud Has to Give It

Whichever service you pick on whichever cloud, the deployment is correct when these six hold. They come from the SDK's own source and runbook and from the gateway's reference deployment, not from any cloud's marketing, which is why the cloud sections below are mostly about how each platform satisfies or violates them.

  1. 1
    A JDK 21 container that you built. The runtime line is JDK 21, Spring Boot 4.1 and Jackson 3, unchanged from 1.0.0 through 5.0.0. The repository's Dockerfile is runtime-only, on eclipse-temurin:21-jre-alpine as a non-root user, and copies in a jar you built outside Docker, because the code generation needs the private specification sibling that no build context carries. No image is published to any registry, for the demo or anything else: you build, you push to your own registry, and you deploy by digest. Build for linux/amd64 on Apple silicon or the container fails at start with an exec-format error.
  2. 2
    One replica, one SQLite file, on local disk. The library requires a sqlitePath and upserts into it on every remote read. Two processes on one file is undefined; the gateway's deploy rule is exactly one replica per store. "Local" means the container's own filesystem or a block volume attached to one instance. It does not mean a network share: SQLite in WAL mode on an SMB mount fails at the first connection with SQLITE_BUSY, as the gateway's member-hosting guide records from its Azure deployment, and NFS (EFS, Filestore, Azure Files over NFS) and FUSE object mounts have the same class of problem. Treat the file as a cache you can afford to lose: syncAllDetails() rebuilds it from the API. What it holds that you cannot rebuild is under go-live. Nothing runs CacheRetention.sweep for you; schedule it.
  3. 3
    Outbound HTTPS, and nothing else, for an outbound-only service. Egress goes to the Connect API host for the environment (connect2.tsanet.org is Production, connect2.tsanet.net Beta; the demo also carries a Development host), to login.microsoftonline.com for the token in client-credentials mode, and to your package registry at build time. Every shipped app refuses a plain-http base URL at startup. Through a corporate proxy the JDK's https.proxyHost and javax.net.ssl.* settings apply, but a default Authenticator for an authenticating proxy does not, because the library moved to java.net.http.HttpClient in 3.0.0; redirects are not followed either. A service that only sends needs no load balancer and no public IP: a private subnet with a NAT route is a complete deployment.
  4. 4
    Secrets in through the environment, read once. Every app binds ${VAR} placeholders at startup, so the source of truth is your cloud's secret store and the delivery mechanism is an injected environment variable (or a mounted file you read yourself). Three consequences hold on all three clouds: rotation is a new value plus a restart, a new revision or a forced deployment, never a live reload; a value must not contain ${, because Spring resolves it inside a bound value; and a value set from a file carries its trailing newline, so set it from an argument. Never in the image, never in a committed file.
  5. 5
    A TLS-terminated public URL only when something comes in. Three things come in: webhook deliveries, the demo's browser traffic, and a receiver's PUT. Terminate TLS at the cloud's edge and let the container speak plain HTTP on 8090 inside. For webhooks the edge must hand over the body byte-for-byte: every delivery is signed X-Hub-Signature-256: sha256=<hex>, HMAC-SHA256 over the raw payload, and anything that re-serializes JSON on the way in makes every signature fail. The console app registers tsanet.webhook.public-base-url as its callback, so that value is the public https URL, not localhost. For the demo the gate is mandatory and /healthz and /.well-known/jwks.json are the only paths outside it.
  6. 6
    An identity for the object store, where there is one. The attachment receiver's S3 adapter uses the AWS default credential chain when no key pair is configured, and its GCS adapter uses Application Default Credentials when no service-account JSON is: a task role, an instance profile or a runtime service account carries the access and no key sits anywhere. The Azure Files and Azure Blob adapters take a SAS URL or a connection string only, with no managed-identity path at 5.0.0, so on Azure that SAS is a secret like the rest. One identity that cannot help anywhere: a managed identity in your tenant does not stand in for the Entra client secret TSANet issued, because the token is minted in TSANet's tenant.

Amazon Web Services

AWS: Express Mode Is the Path That Has Been Run

runthe SDK web demo on Amazon ECS Express Mode since 2026-10-29, moved there from App Runner documentedplain ECS, EKS and the storage and secrets rules, read from AWS documentation on 2026-11-06

TSANet's own hosted demo runs on Amazon ECS Express Mode: one Fargate task behind a managed Application Load Balancer with TLS, created from the image the repository's Dockerfile builds, with the procedure in the SDK runbook's section 6. It replaced an App Runner service because App Runner stopped accepting new customers on 2026-04-30; existing services keep running with no announced shutdown date, and AWS names Express Mode as the successor. One difference matters to the build: App Runner could build from source, Express Mode takes an image only, which for this SDK was already the only option.

What Express Mode gives a single container is close to what a demo or a small integration service needs and nothing more: a URL of the form https://<name>.ecs.<region>.on.aws with TLS terminated, a target-group health check on the path you name (/healthz for the demo), CloudWatch logging, and canary deployments with 5XX rollback alarms on every update. Express Mode itself is free; you pay for the Fargate task, the load balancer and the logs for as long as the service exists. The demo runs at 0.25 vCPU and 512 MiB.

What the runbook learned the hard way

  • Two IAM roles, and IAM is eventually consistent. A task execution role (trusting ecs-tasks.amazonaws.com, with AmazonECSTaskExecutionRolePolicy plus permission to read your parameters) and an infrastructure role (trusting ecs.amazonaws.com, with AmazonECSInfrastructureRoleforExpressGatewayServices). A create that runs within a minute of making them fails with a permissions message; the first create on a new account can also fail with "Unable to assume the service linked role" and succeed on a retry, because that call creates the role.
  • Secrets ride in secrets[].valueFrom. SSM Parameter Store SecureStrings (or Secrets Manager ARNs) named in the container definition arrive as environment variables, resolved when the task starts. AWS states the rule plainly: if the secret changes, force a new deployment or launch a new task. The runbook observed that an update-express-gateway-service with an identical container block still starts a new deployment, which is the rotation mechanism.
  • Pin the SHA tag, not latest. The container definition names <registry>/connect-sdk-demo:<sha> so describe-express-gateway-service always says which build is running. The first deployment takes about twelve minutes while the load balancer and alarms are provisioned; a redeploy is a canary.
  • There is no pause. The service bills while it exists, and the URL is minted per service: delete and recreate to save money and every link you handed out dies. The demo runs with minTaskCount and maxTaskCount both at 1; the console defaults are 1 and 20. The ExpressGatewayScalingTarget reference gives no valid range for the minimum, so whether Express Mode accepts a floor of 0 is not stated and has not been tried needs probe.
  • ARM64 is on offer; the image is amd64. Express Mode can run Graviton tasks, but the repository's build is linux/amd64. Match the two or the task exits on start.

Storage, and the two things that are not ECS Express

A Fargate task gets 20 GiB of ephemeral storage by default (up to 200), encrypted, and deleted with the task. That is the right home for the SQLite cache: the demo's data directory lives there and is re-seeded from SSM on every start, and a service of your own can rebuild its cache with one call. Amazon EFS is NFS, so it is not where the live file goes; if a file must survive, copy it to S3 on a schedule from a sidecar, which is the pattern the gateway's guide prescribes (its AWS section is written but has not been run).

Plain ECS on Fargate with your own task definition is the step up when you need what Express Mode's one-call form hides: a task role (the receiver's S3 adapter picks it up with no keys configured), a private subnet with a NAT route and no load balancer at all for an outbound-only service, a sidecar container, or Secrets Manager's rotation. Express Mode accepts a bring-your-own task definition too, provided the container is named Main with one port mapping and the family is Fargate-compatible, so you can start on the short form and graduate without leaving the service.

Amazon EKS is for members who already run Kubernetes. The rules translate directly: a Deployment with one replica and the Recreate strategy, not RollingUpdate, so two pods never overlap on one volume; an emptyDir or a single-attach gp3 volume through the EBS CSI driver for the cache, never EFS; secrets into environment variables through the Secrets Store CSI driver or External Secrets; IAM roles for service accounts for S3. AWS Lambda is the wrong shape: a Spring Boot process with a local database, a renewed bearer token and a webhook secret on disk is a long-lived service, not a function.

Microsoft Azure

Azure: Container Apps, with the One Failure Already Found for You

runthe Connect Gateway engine, which embeds this SDK, on Azure Container Apps as the member-hosting reference written, not runthe SDK demo's Container Apps procedure, taken from Microsoft Learn on 2026-08-04 with no subscription to execute it documentedApp Service, AKS, billing, secrets and storage, read from Microsoft Learn on 2026-11-06

Azure Container Apps is the analogue of Express Mode: an image in, a managed HTTPS hostname out, and a replica count that can reach zero. Two TSANet documents cover it from opposite directions. The SDK repository's docs/azure-deployment.md walks the demo onto it command by command and is honest that nobody has executed it; the gateway's member-hosting guide was executed, on the engine that embeds this same library, and is where the hard finding below comes from.

The recipe, and the gotcha on line one

A registry (az acr create), a user-assigned managed identity with AcrPull so no registry password lives in the app, a Container Apps environment, and then one create with --target-port 8090 --ingress external --min-replicas 0 --max-replicas 1, the gate password in --secrets and referenced from the environment as secretref:. The gotcha is the registry hostname: ACR's domain-name-label feature appends a hash, so a registry named connectsdkdemo answers at something like connectsdkdemo-e7gg….azurecr.io, the scope is immutable after creation, and a script that assumes <name>.azurecr.io fails with an image-pull error that reads like a permissions problem. Read loginServer from the create output.

Scaling and what it costs

On the Consumption plan a revision scaled to zero incurs no resource-consumption charge; a revision kept at a minimum above zero is billed at an idle rate while it sits idle. An environment with only Consumption workload profiles carries no plan-management fee; a Dedicated profile does. So a demo can sit at zero between calls and pay a JVM cold start on the first request, and a service that works between requests (webhook post-processing, a scheduled sync or sweep) keeps one replica at the idle rate. Send one warm-up request before a demo.

Secrets, and the revision that does not happen

Secrets live in the app's own secret store or as Key Vault references (keyvaultref: plus a managed identity holding the Key Vault Secrets User role). Microsoft's rule, which bites exactly where you would expect: adding, removing or changing a secret does not create a revision, and an updated secret does not affect a running revision until you deploy a new revision or restart the existing one. The one case the platform handles for you is a Key Vault reference without a version: the app picks up a new version within 30 minutes and active revisions that use it in an environment variable are restarted automatically, which for a single-replica service is the rotation restart done on your behalf.

Storage: the finding

A container app has its own filesystem (1 GiB at a quarter vCPU, rising to 8 GiB above one vCPU, shared with any replica-scoped EmptyDir volume) that disappears with the container, and Azure Files over SMB or NFS as the only durable mount, shared across replicas. The live SQLite file goes on the first, never the second: the gateway's member-hosting guide records that on an Azure Files SMB mount the database fails at the first connection with SQLITE_BUSY, which is why its reference spec keeps the files local. The pattern that shipped is the database on local disk plus a backup sidecar that copies the files to an Azure Files share every five minutes and keeps hourly snapshots for 48 hours, restored on start. One more reason the live file is local: in single-revision mode Container Apps starts the new revision before stopping the old one, so for a short window two replicas run, and a shared file would have two writers.

Deploy by digest. az containerapp update --image creates and activates a revision, and the pull policy is always always, but an update whose template is unchanged (the same tag string after you pushed new code under it) is not a configuration change and rolls nothing; the gateway page records that exact no-op on this platform. The receiver's Blob and Files adapters want a SAS URL or connection string, so that value goes in Key Vault with the rest, with rw (or rcw) on the container.

App Service and AKS

Azure App Service (Java SE on Linux) is for teams that already run it: you deploy the executable jar with az webapp deploy --type jar and there is no container to build, and Java 21 is a supported runtime. Two things to set deliberately. The built-in image starts the jar on port 80, so the demo's and the console's 8090 have to be overridden in the startup command. And /home is persisted, shared storage, which is a network share (the platform's own JAVA_COPY_ALL setting exists "to address file-locking issues" on it), so the SQLite path belongs outside /home, where it is per-instance and gone on restart, exactly as on a container. App Service does not scale to zero; run one instance with Always On.

AKS follows the EKS rules: one replica, Recreate, an Azure Disk (block) volume or emptyDir for the cache and never an Azure Files volume, Key Vault through the Secrets Store CSI driver. Workload identity is welcome for everything except the two things it cannot replace: the receiver's SAS, and the Entra client secret for the Connect API, which TSANet's tenant issues.

Google Cloud

Google Cloud: Cloud Run Fits, with Two Settings That Decide It

documentednothing SDK-side has been run on Google Cloud by TSANet; everything here is read from Google's documentation on 2026-11-06 spec-readGoogle Cloud Storage is a direct-delivery receiver store in the API specification; the SDK's registration facade covers S3 and Azure Blob only, while the receiver library does ship a GCS adapter

Cloud Run takes the same image from Artifact Registry, gives it an HTTPS run.app URL, and scales to zero by default: minimum instances is 0 unless you raise it, and an idle instance is kept at most 15 minutes. Set the service's container port to 8090 and the demo listens where Cloud Run sends. The container must be listening within four minutes of start (startup CPU boost shortens a JVM boot), gets SIGTERM and ten seconds at shutdown, and must answer every request inside the configured request timeout, which for the demo means a timeout long enough for the largest attachment you will push through one request.

Setting one: CPU allocation

Cloud Run's default is request-based billing, where "CPU is only allocated during request processing". Everything an SDK service does between requests runs without CPU in that mode: the console's cache sync after it has answered a webhook, a scheduled syncAllDetails or CacheRetention.sweep, the library's token renewal ahead of expiry. Any shape that works outside a request needs instance-based billing ("CPU is always allocated"), which bills for the instance's whole life, together with a minimum of one instance so there is a process to do the work. A pure request-and-response wrapper around the library can stay request-based.

Setting two: maximum instances

Cloud Run scales out on load. Two instances are two SQLite caches, and with v1 webhooks they are worse than that: the subscription's HMAC secret exists only in the cache of the instance that created it, so the other instance reports every delivery as unsigned. Set maximum instances to 1.

Filesystem, secrets, identity

The writable filesystem is in memory: "writing to it uses the instance's memory", and "data written to the file system doesn't persist when the instance stops". The SQLite cache therefore sits inside the memory limit, which makes the retention sweep a sizing matter rather than housekeeping, and it is lost on every instance replacement, not only on every deploy. The demo's seeds and lock were built for precisely this (credentials and partner keys re-created at start from secrets). Cloud Storage FUSE volumes are durable but "do not provide concurrency control for multiple writes (file locking) to the same file" and "the last write wins", so they are a backup target, never the live database.

Secrets come from Secret Manager as environment variables (resolved at instance startup; Google recommends pinning a version rather than latest) or as mounted files (the latest version is fetched on each read). The runtime service account needs the Secret Manager Secret Accessor role. Since every shipped app reads its configuration at startup, rotation is a new version plus a new revision either way. The receiver's GCS adapter uses Application Default Credentials when no credentialsJson is configured, so the same runtime service account, granted object write on the bucket, carries storage access with no key file in any configuration.

GKE Autopilot for Kubernetes shops: one replica, Recreate, a Persistent Disk (block) volume or emptyDir and never Filestore, Workload Identity Federation for GCS, Secret Manager through the add-on or External Secrets.

Sharp edges

The Go-Live List, in the Order It Bites

  • There is no image to pull, and the build needs the private specification. A member consuming the artifact builds its own service and this is a non-issue. Anyone hosting the demo or the console builds from source with read access to the specification repository, or asks TSANet for a jar or image. Settle that before the cloud account, not after.
  • The demo's gate is the whole security model. With TSANET_DEMO_AUTH_PASSWORD unset it runs open; behind it sit live member credentials and the ability to page a partner's engineer with a real case. A guest login (TSANET_DEMO_AUTH_GUEST_*) gives members a second password with a lower upload limit. The demo will not talk to Production at all; a service of your own will, so keep Production credentials in the production deployment only.
  • One writer, enforced by the deploy strategy. Kubernetes: Recreate. Container Apps: single-revision mode overlaps old and new, harmless on local files and fatal on a shared one. Cloud Run: maximum instances 1. Express Mode: a canary briefly runs two tasks, each with its own ephemeral disk, so two caches and never two writers.
  • Know what the filesystem takes with it. The cache rebuilds. Two things do not: a v1 webhook subscription's HMAC secret, which the API returns once at creation and the library stores only in your webhook_subscription row; and the demo's per-environment credentials and partner-key table, which you seed instead (TSANET_DEMO_SEED_*, TSANET_DEMO_E2EE_PARTNERS_*, with TSANET_DEMO_CREDENTIALS_LOCKED so visitors cannot change them). For the secret, either back the file up to object storage on a schedule or plan to create a new subscription after a loss and delete the old one, which keeps delivering until you do.
  • The SDK's webhook client is v1, and v1 sunsets on 2027-01-01. A receiver built on receiveInbound has a clock on it whatever cloud it runs in. The v2 CloudEvents contract, including OAUTH2_CLIENT_CREDENTIALS callback auth, which means your edge also fronts a token endpoint, is on the API page. Hosting does not change this; it just makes the endpoint real.
  • Raw bytes for the signature. HMAC-SHA256 over the body as delivered, compared against X-Hub-Signature-256. An API gateway that pretty-prints JSON, or a framework that re-serializes before your handler, breaks every verification silently: the library records signatureValid=false on each event and nothing errors.
  • Rotation is a restart, everywhere. New value in the secret store, then a forced deployment (ECS), a new revision or restart (Container Apps), a new revision (Cloud Run). No ${ in any value; set values from arguments, not files.
  • Cold starts are real. A Spring Boot 4 process on a quarter vCPU takes a while to listen. Warm a scaled-to-zero demo before the call, and give a startup probe room before a liveness probe can kill it.
  • The proxy that is not there. Egress through a corporate proxy works with https.proxyHost; an authenticating proxy needs something in front of the process, since the JDK client the library uses ignores a default Authenticator.
  • Logs are safe by design; keep them that way. ConnectApiException messages carry no URL, header or token, the receiver's storage errors carry no credential, and the demo's key generator prints the private JWKS once to standard output and nowhere else. Don't undo that with a docker inspect pasted into a ticket; AWS's own guidance prefers file-mounted secrets to environment variables for the same reason.
  • Sweep the cache. CacheRetention.sweep evicts closed and rejected cases by age and never touches an open one, and nothing calls it for you. On Cloud Run it is your memory budget.
  • Pin by digest. A moved tag rolled nothing on Container Apps; the ECS runbook pins SHA tags so the running build is always readable from the service description. The gateway's guide deploys by sha256: digest for the same reason.
Cloud Run is the gap: nothing SDK-based has been run there and reported back. If you host on Google Cloud, or on anything not listed, say so in Community with what you had to change; the platform rows above are only as good as the deployments behind them. The deployment skill carries the runbook knowledge in a form a coding assistant can apply while it plans your deployment.
